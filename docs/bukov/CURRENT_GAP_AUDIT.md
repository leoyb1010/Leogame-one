## 1. 状态和优先级口径

| 标记 | 含义 |
|---|---|
| ✅ 已完成 | 已有可用实现，并且至少存在对应的源码级自动测试或明确宿主接入 |
| 🟡 仅模型未接入 | 数据模型、算法或测试已存在，但真实游戏流程没有消费它 |
| ❌ 完全缺失 | 当前仓库中未发现规格要求的实现 |
| ⚪ 验收证据缺失 | 可能已有部分实现，但没有保留下来的自动报告、截图、录像、性能数据或双端包证明其通过 |
| P0 | 阻断“第一关从配装到结算可完整玩”的问题 |
| P1 | 阻断“高品质、可发布、可长期扩展”的问题 |

“存在一个 Java 类”不等于完成。只有当模型被真实场景调用、状态可持续保存、用户能通过 UI/手柄完成流程，并留有自动与人工证据时，才能按 Gate 验收。

## 2. 执行结论

### 2.1 已经真正形成的工程资产

- ✅ Leogame-one 已作为唯一宿主工程，基线 SHA、分支、工具链与 Unity 原型只读盘点已记录。
- ✅ 标题页已有“逃离布科夫 · ESCAPE FROM BUKOV”入口，布科夫模式使用独立存档槽 `100`。
- ✅ `FixedStepClock`、`RealtimeRaidSystem`、`RealtimeBody`、网格碰撞、实时输入和浮点精灵定位已接入 `GameScene`、`Char`、`CharSprite`。
- ✅ 实时模拟顺序已经被集中在 `RealtimeRaidSystem`，这是后续战斗、AI、拾取和撤离接入的正确主干。
- ✅ 枪械定义、弹药、射击控制、hitscan、伤害和抛射体模型及对应测试源文件已存在。
- ✅ `RaidItem`、`LootTransaction`、`BukovStash`、`BukovProfile`、`RaidSettlement`、`ExtractionState` 等局外/结算模型已存在，结算模型考虑了原子内存提交与幂等重放。
- ✅ 首关语义地图规划、三路线/撤离定义、校验器和 seed 扫测源文件已存在。

### 2.2 当前最危险的误判

- 不能把枪械单元测试理解为“游戏里已经能开枪”。`BukovRealtimeWorld.emitPlayerActions()` 仍明确标注 Gate 2 才接入 `FireControl`。
- 不能把地图图模型理解为“首关已经可玩”。当前未发现 `BukovLevel` 或连接 `RegularLevel`/房间绘制系统的适配器。
- 不能把 Bundle 往返测试理解为“存档已经可靠”。当前没有 `BukovSaveService`、原子文件替换、备份恢复或独立的局内存档文件。
- 不能把结算模型理解为“已经能搜打撤”。当前没有场景战利品容器、拾取交互、撤离物件、局内结算触发或局外仓库 UI。
- 不能用既有 Shattered Pixel Dungeon 的美术、动画和 HUD 证明布科夫品质。布科夫专属 UI token、HUD、枪口/曳光/命中 VFX、枪声、敌人动画和品牌资源尚未接入。
- 不能用基线编译结果证明当前脏工作树可交付。HEAD 与 `origin/main` 相同，全部布科夫工作仍是未提交修改或未跟踪文件。

## 4. 按关键系统的实时差距

### 4.1 存档、仓库、战利品、撤离和结算

| 能力 | 现状 | 缺口 | 验收证据要求 | 判定 |
|---|---|---|---|---|
| Profile 数据 | `BukovProfile` 含版本、货币、仓库、统计、地图/合同和结算记录 | 没有文件服务、迁移入口、失败回滚或损坏恢复 | profile 文件往返、跨版本迁移、损坏文件回退 | 🟡 |
| 局内 Session | `RaidSession` 可创建、计时、Bundle 序列化 | `GameScene.create()` 每次新建 session；继续游戏可能把 elapsed/settled 重置 | 中途退出再继续，seed、计时、战利品、撤离进度一致 | 🟡 |
| 独立文件 | 无 `BukovSaveService` | 缺少 `bukov_profile.dat`、`bukov_raid.dat`、临时文件、原子替换和备份 | 强杀/断电模拟后不丢 profile；raid 成功后正确删除 | ❌ |
| 仓库模型 | `BukovStash` 支持存取、复制、Bundle | 无仓库场景、筛选、堆叠、容量/装备交互 | 键鼠与手柄完成存入、取出、配装 | 🟡 |
| 局内负重 | `LootTransaction` 计算数量、重量、价值与指纹 | 未接玩家属性、移动速度、背包容量或 HUD | 超重拒绝/惩罚、HUD 同步、跨存档一致 | 🟡 |
| 战利品容器 | 无真实容器实现 | 缺搜索计时、掉落表、可见/未知状态、打断、拾取和地面掉落 | 搜索 3 个容器，退出/继续后内容不重掷 | ❌ |
| 原有物品系统适配 | 当前未发现 `Bag`/`Backpack`/`Item.collect`/`Heap` 与 Bukov 模型的适配器 | 同一物品可能出现双数据源；缺 UID 与旧 Item 的边界定义 | UID 唯一、无负数、无重复领取、掉落/拾取闭环 | ❌ |
| 撤离状态 | `ExtractionState` 支持条件、倒计时、打断、轻伤衰减和 Bundle | 未生成世界撤离点；未接交互输入；未与地图 `ExtractionDefinition` 统一 | E01/E02/E03 在实机可进入、打断、完成并正确提示 | 🟡 |
| 撤离定义一致性 | `levels.ExtractionDefinition` 与 `raid.ExtractionState` 各自存在 | 缺少唯一权威定义或转换层，容易条件/时间配置漂移 | 注册表单源 + 映射测试 | 🟡 |
| 成功结算 | `RaidSettlement` 成功时转移携带物、记录 receipt | 世界逻辑从未调用 settle；无结算场景；无存档事务 | 成功撤离只发放一次，重启后仍不可重复领 | 🟡 |
| 死亡结算 | 模型会统计丢失价值且不入仓 | 玩家死亡未接局内事务；基础装备/安全箱规则未接 | 死亡、强退、重进三路径结论一致 | 🟡 |
| 幂等 | receipt + fingerprint 防止同 raid 重复结算 | 仅内存/Bundle 层；没有文件提交和崩溃窗口证明 | 至少 30 组自动结算 + 写文件中断注入 | 🟡 |
| 局外配装 | 无 | 不能选择枪、弹药、护甲、背包和医疗物资进入 raid | 配装合法性、容量、弹药匹配、手柄全流程 | ❌ |

**P0 结论：** Gate 3 最有价值的事务模型已经具备，但现在仍是“库代码”，不是玩家可触达功能。下一阶段必须优先建设持久化和世界/UI 接线，不能继续只加数据类。

## 6. P0：下一里程碑必须完成的阻断项

目标不是“继续堆模型”，而是做出一条可以反复验证的最小搜打撤闭环。

### P0-1：形成可追踪检查点

1. 对当前共享工作树完成源码冲突检查和一次统一测试。
2. 更新 `IMPLEMENTATION_MATRIX.md` 使其与真实状态一致。
3. 将通过验证的实时、战斗、raid 和地图模型提交到独立 SHA。
4. 从此每个自动报告、录像和设备测试均记录 SHA。

完成标准：工作树和测试结果能对应到唯一提交；不是依赖某个代理口头报告。

### P0-2：实现真正的 Bukov 存档服务

建议最小接口：

```java
public interface BukovSaveService {
	BukovProfile loadProfile();
	void saveProfile(BukovProfile profile);
	RaidSnapshot loadRaid();
	void saveRaid(RaidSnapshot raid);
	void deleteRaid();
}
```

必须包含：

- profile 与 raid 分文件，避免一次局内损坏摧毁长期仓库。
- 同目录临时文件写入、flush/close、原子替换；不支持原子移动的平台使用可验证备份回退。
- `profileVersion`/`raidVersion` 与迁移入口。
- `RaidSession`、携带物、地图 seed/布局、撤离状态、玩家关键状态和已结算标记。
- 成功/死亡结算采用“先得到新 profile → 持久化 → 标记 receipt → 删除 raid”的明确崩溃恢复协议。
- 重复启动或重复提交同一 raid 不能重复发货。

完成标准：中途退出、强杀、成功后重启、死亡后重启、写入中断五条测试均通过。

### P0-3：把语义图变成真实首关

建立一个薄适配层，将 `BukovRaidLayout` 映射到宿主 `Level`：

```java
public final class BukovLevelAssembler {
	public Level build(BukovRaidLayout layout, long seed);
}
```

最小首关只需要：

- 玩家出生区。
- 三个可搜索容器。
- 一条主路线和一条替代路线。
- 一个敌人战斗房。
- 一个标准撤离点。
- 门、墙、碰撞、FOV 和返回地图标识可保存。

完成标准：固定 seed 每次产生同一可走地图，且布局中的路线/撤离元数据与世界实体一一对应。

### P0-4：接通一把枪和一个实时敌人

把现有模型按 `RealtimeRaidSystem` 顺序接入：

```text
输入/开火
  -> FireControl
  -> HitscanResolver / RealtimeProjectile
  -> DamageEvent
  -> RealtimeDamage
  -> Enemy health/death
  -> Loot drop
```

最小敌人必须具备：

- 视野或声音感知。
- 追击/保持距离中的一种。
- 开火、换弹、受击、死亡。
- 死亡后掉落一个带唯一 UID 的物品。

完成标准：玩家能用 `ward_556` 或一把明确的基准枪完成装弹、射击、击杀、拾取；自动测试和实机录像同时存在。

### P0-5：接通最小局内外流程 UI

必须同时实现：

1. 仓库/配装。
2. 局内 HUD。
3. 容器搜索与拿取。
4. 撤离进度和条件提示。
5. 成功/死亡结算。

所有界面从第一天支持：

- 键鼠。
- 手柄方向/摇杆焦点。
- 确认、取消、返回。
- 弹窗关闭后焦点恢复。
- 长列表滚动。

完成标准：不用调试键、控制台或鼠标“救场”，手柄可独立完成一次完整闭环。

### P0-6：建立端到端验收

最小 smoke：

```text
创建/加载 profile
  -> 从仓库给玩家装配 1 枪 + 2 弹匣
  -> 进入固定 seed
  -> 搜索 3 个容器
  -> 击杀 1 个敌人
  -> 拾取掉落物
  -> 完成撤离
  -> 结算入仓
  -> 重启
  -> 验证仓库物品与 receipt
  -> 再开一局死亡
  -> 验证携带物丢失且不可重复结算
```

需要的证据：

- 自动 smoke 日志。
- macOS 完整录像。
- iOS 模拟器或真机完整录像。
- 同一 SHA 的测试摘要。
- 存档前后摘要和 UID/数量不变量检查。

## 7. P1：高品质与交付完善

P0 闭环通过后按以下顺序推进：

1. **内容完整度**：补到 6 枪、5 弹、3 甲、2 包、8 医疗/工具、30 战利品、4 敌人+精英+Boss、3 撤离点。
2. **UI 设计系统**：建立 `ui_tokens.json`、统一组件、焦点态、危险/稀有度/容量状态和多分辨率布局。
3. **动画和打击感**：角色/敌人状态机、枪口、曳光、命中、受击、死亡、掉落、可关闭屏震与闪烁。
4. **音频**：枪声、装填、空仓、命中、脚步、敌人状态、环境和撤离；控制混音和并发上限。
5. **地图视觉**：6 类语义房专属可读性、路线地标、撤离识别、像素密度/调色/采样统一。
6. **AI 与战术**：声音场、视野、掩体/距离、协同、精英/Boss，但必须沿用同一实时钩子，不另建第二套循环。
7. **性能基线**：加入 smoke/soak 脚本、30 敌人+200 反馈对象场景、P50/P95/P99、GC、加载和存档指标。
8. **双端验收**：macOS 可分发包、iOS AOT/模拟器/真机、120/60 Hz、手柄、离线和恢复。
9. **来源合规**：补 `SOURCE_PROVENANCE.csv`、`THIRD_PARTY_NOTICES.md`、素材 hash、许可证、修改说明和不可用来源清单。
10. **第 82 节体验验收**：12 项逐项记录 SHA、设备、录像/截图和结果，全部绿灯后才称“第一关完成版”。

## 8. 建议的下一阶段完成定义

下一阶段名称：**Gate 3 Vertical Slice — 最小完整搜打撤闭环**。

只有同时满足以下条件才算完成：

- 一个提交 SHA 同时包含真实关卡、开火、敌人、容器、撤离、结算和文件存档接线。
- 自动测试覆盖成功、死亡、重复结算、存档中断和中途继续。
- macOS 键鼠与手柄均能完整走通。
- iOS 至少一个模拟器或真机完整走通。
- 从游戏 UI 可完成，不使用调试入口。
- 画面可以仍是首轮资源，但必须有清晰 HUD、动作状态和命中反馈，不能再只是灰盒。
- 所有证据放入 `docs/bukov/evidence/` 并绑定 SHA。

在这个里程碑之前，不建议把主要工时投入到更多地图、更多枪或 Boss；否则会继续扩大“模型存在、游戏不可玩”的集成债务。

## 9. 发布阻断结论

当前仓库可以作为**有正确技术方向的早期实时搜打撤原型**继续开发，但不能称为“第一关可玩版”“高品质版本”或“已完成计划书”。最关键的差距不是代码数量，而是以下五条尚未同时成立：

1. 枪战模型进入真实运行时。
2. 地图模型进入真实关卡。
3. 战利品/撤离/结算进入真实场景与 UI。
4. profile/raid 具有可恢复的原子文件持久化。
5. macOS/iOS 对同一提交留下完整流程和性能证据。

解除这五项后，项目才从“并行开发出的模块集合”进入“可连续游玩的游戏”；随后 Gate 5/6 的音画、交互、性能和发布完善才有稳定承载面。
